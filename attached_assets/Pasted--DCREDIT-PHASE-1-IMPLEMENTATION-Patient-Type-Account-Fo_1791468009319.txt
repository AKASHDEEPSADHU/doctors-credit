# DCREDIT — PHASE 1 IMPLEMENTATION
## Patient Type + Account Foundation + Initial Assessment Payment

You are working on the existing DCREDIT / Doctors Credit application.

**IMPORTANT: This is PHASE 1 ONLY.**

Do not implement, partially implement, scaffold, redesign, or modify functionality belonging to later phases unless a small database/API foundation is strictly required for Phase 1 compatibility.

The objective is to safely implement the first production-grade step of the finalized DCREDIT patient journey:

> Patient identifies as Domestic or International → signs in → starts Initial Patient Assessment → sees the correct server-controlled price → completes secure payment → payment is verified server-side → account/payment state is persisted.

# 2. PHASE 1 SCOPE

Phase 1 includes ONLY:

### A. Patient type
The user must be able to identify as:

- Domestic Patient
- International Patient

This selection must be persisted against the authenticated account/session/case context as appropriate.

### B. Authentication
Use the existing Google OAuth.

After successful Google authentication:

- create or retrieve the persistent application account
- use Google's stable provider/user ID rather than relying on display name
- persist verified email
- do not create a separate password system
- do not store OAuth passwords

The same Google account must retrieve the same application account on future logins.

### C. Initial Patient Assessment payment

The initial service is:

**Initial Patient Assessment / Initial Patient Assistance & Medical Coordination Fee**

Pricing:

| Patient Type | Amount | Currency |
|---|---:|---|
| Domestic | ₹999 | INR |
| International | $15 | USD |

The patient must NOT be able to modify the amount or currency.

The browser/client must never be considered the authority for:

- amount
- currency
- patient type
- payment status

The server must determine and validate these values.

# 3. IMPORTANT PAYMENT POSITIONING

Do not describe the ₹999 / USD 15 payment as merely a:

> Doctor Registration Fee

The service should be positioned as an initial:

**Patient Assessment / Patient Assistance & Medical Coordination Fee**

The payment is for coordination and treatment-planning assistance.

Do not imply that DCREDIT itself provides diagnosis or medical treatment.

Medical decisions, diagnosis, treatment recommendations and procedures remain with qualified healthcare professionals.

# 6. DOMESTIC VS INTERNATIONAL PAYMENT

The server must determine pricing based on patient type.

### Domestic

Domestic patient:

```text
Amount: 999
Currency: INR
```

### International

International patient:

```text
Amount: 15
Currency: USD
```

Do NOT display both prices in a confusing manner during checkout.

For example, a domestic patient should primarily see:

> Initial Patient Assessment  
> ₹999 INR

An international patient should primarily see:

> Initial Patient Assessment  
> USD 15

International card issuers may independently convert USD into the cardholder's local currency.

Do not promise a particular local-currency amount.

---

# 7. SERVER-SIDE PRICE ENFORCEMENT

Implement a single server-side source of truth for Phase 1 pricing.

Conceptually:

```text
DOMESTIC → INR 999
INTERNATIONAL → USD 15
```

The server must validate:

1. authenticated account
2. patient type
3. requested service
4. expected currency
5. expected amount
6. existing payment status
7. payment/order state

Never trust:

```text
amount
currency
patientType
paymentStatus
```

from the browser.

If the client sends an amount, treat it only as a request and independently calculate the authoritative value on the server.

---

# 8. PAYMENT FLOW

Implement this sequence:

```text
Google Login
      ↓
Account Created / Retrieved
      ↓
Patient Type Selected
      ↓
Initial Assessment Selected
      ↓
Server Calculates Price
      ↓
Checkout Summary
      ↓
Payment Order Created Server-Side
      ↓
Hosted/Secure Payment Checkout
      ↓
Payment Provider Processes Payment
      ↓
Provider Webhook / Server Verification
      ↓
Server Confirms Payment
      ↓
Payment Record Updated
      ↓
Initial Assessment Payment Activated
      ↓
Confirmation Screen
```

### Critical rule

A redirect back from the payment provider is NOT proof of successful payment.

Only:

- verified provider response
- webhook
- or equivalent server-side verification

may mark a payment as successful.

# 10. DUPLICATE PAYMENT PREVENTION

A patient/account must not accidentally pay the same Initial Patient Assessment twice.

Before creating a new checkout:

1. Check whether the account already has a confirmed Initial Patient Assessment payment.
2. If yes:
   - do not create another assessment payment
   - show that the assessment payment has already been completed
3. If an earlier payment is only `pending` or `failed`, handle it safely according to the existing payment architecture.

The webhook must also be idempotent.

If the same webhook is received multiple times:

- do not create duplicate payment records
- do not activate the assessment multiple times
- do not create duplicate downstream records
